# Aardwolf firmware

This app implements the [Aardwolf ADR](../../SpecAndDesign/ADR/apps/app/_aardwolf/ADR%20Aardwolf%20GPS-Calibrated%20Audio%20Logger.md) for Raylar v1.0. It starts in energy recovery, powers GPS and the microphone only after reported battery SOC exceeds 20%, and pauses audio, GPS, and enabled radio when SOC falls below 10%. With radio enabled, heartbeats resume at the next complete UTC half-hour epoch after recovery.

**Default diagnostic configuration:** the radio service is enabled again, with both `sd-diagnostics` and `radio-diagnostics`. Startup identifies all three flags. The default six-channel cheap CRCL codec, GPS policy and file cadence are unchanged. To repeat the radio-disabled comparison, select `--no-default-features --features firmware,core-smps,cheap-crcl,sd-diagnostics,radio-diagnostics`: omitting `radio` holds the module in reset and starts no radio driver/coordinator/recovery tasks. Independent telemetry remains and reports `radio=Disabled`.

GPS green follows the shared UI policy: solid while the powered receiver is searching or reacquiring, a 50 ms pulse for each new GPS PPS anchor accepted by the Time Service while tracking, and off in standby, power transitions, receiver error, or off. Receiver state is checked every 50 ms independently of buzzer playback, so the search indication does not wait for PPS or a time publication.

Build with `cargo build -p aardwolf --release --target thumbv8m.main-none-eabihf`. The binary is `target/thumbv8m.main-none-eabihf/release/aardwolf`. No automatic flashing is part of the build.

After opening `syslog.txt`, startup drains the existing log queue, writes compact device/firmware and SD identity records, drains them and checkpoints the file before starting audio. The `versioning sd_card=known` record includes manufacturer ID, OEM ID, product name/revision, serial number, manufacture date and physical capacity in bytes. A backend without card identity emits `versioning sd_card=unavailable`. Filesystem total/free/cluster sizes are logged separately as `storage ready`. This prevents startup radio diagnostics from dropping identity records out of the bounded 32-record queue; queue memory is unchanged.

`bench-external-power` bypasses the boot SOC gate for externally powered bench work, while still applying the below-10% pause once a valid SOC is reported. It must stay disabled for the solar run. `bench-rx-beep` enables a short audible indication for each valid heartbeat received; field builds leave it disabled.

With the `radio` feature, the fixed RF configuration is in `config.rs`: 868.1 MHz and 2441 MHz, twelve ordered profiles, a 30-minute UTC epoch, and 16-byte V4 heartbeats. Nodes must run the same network and schedule version. Slot permutation is based on NodeId, epoch and profile minute. Minutes 4 and 12 use two-second slots. Quiet periods (minutes 13–30, invalid UTC, and energy recovery) use retained sleep. The driver treats BUSY-high as normal in sleep, wakes with a 100 µs NSS pulse before waiting for BUSY-low, and uses the internal LF RC clock. See the [sleep fault investigation and target validation](../../analysis/radio_sleep/20261018/report.md). Detailed radio timing logging remains enabled.

Audio uses the mono 16 kHz reference microphone configuration and creates one 32-bit FLAC per UTC minute in hourly folders, using 2048-sample blocks. Partial final frames preserve the actual sample count. The encoder is heapless and selects fixed predictors of orders 0–4 and Rice parameters by encoded size, with constant and verbatim fallbacks. FLAC files use frame CRCs; the optional STREAMINFO MD5 is deliberately absent. A file is opened exclusively after its first PCM arrives, so an empty segment creates no file and a repeated timestamp cannot append to or overwrite an earlier recording. Audio starts only when the card has room for a worst-case uncompressed FLAC minute, metadata and frame overhead, plus the 100 MB log reserve. System and radio events are written to the normal system log when the card is available; a missing card leaves the radio and heartbeat task running with storage error bits set.

WAV remains the repository's default recording format and the Audio Recorder Service's `new` constructor. Aardwolf explicitly uses `new_flac_with_buffers` with const-initialized static workspace. The [FLAC service ADR](../../SpecAndDesign/ADR/services/audio/Service%20FLAC%20Encoder.md) records the codec and lifecycle design. Independent decoder checks and the SD fixture test are documented under [servicetests/flacencoder](../../servicetests/flacencoder/README.md); sustained capture with concurrent radio/logging still needs hardware validation.

Every ten seconds, `audio timing` records maximum codec and append time plus peak source backlog. In mono mode, the frame budget is 128,000 microseconds and retention is 128,000 samples (eight seconds). Codec timing includes executor yields; append timing includes the shared storage lock wait. A growing backlog means recording is not keeping pace even while individual FLAC frames remain valid.

Hexaphonic recording with the cheap CRCL v2 codec is enabled by default: acquire MIC1..MIC6 and record a `.CRCL` companion beside each mono FLAC minute. To build mono explicitly, use `--no-default-features --features firmware,core-smps`. MIC1 retains the existing lossless signed 32-bit reference PCM. MIC2..MIC6 use independent in-place shift quantization, 1024-frame blocks, a 10-bit retained target and a minimum six-LSB discard in unpacked PCM units. Each channel/block uses `max(peak_shift, 6)` in one rounding operation, followed by temporal-only prediction and estimated Rice k. Louder blocks may require a larger shift to fit the retained target. `config.rs` exposes the block length, retained precision and minimum shift. See the [noise/precision analysis](../../docs/audio/multichannel/analysis001.md), [multichannel ADR](../../SpecAndDesign/ADR/services/audio/Service%20Multichannel%20Audio%20Recording.md) and [target checks](../../servicetests/crclencoder/README.md).

Hexaphonic recording uses one source reader and one paired lifecycle. Both files share the UTC filename stem, segment identity, sample interval and final sample count. Storage admits the entire pair plus the protected log reserve before opening either member; three stream slots permit the reference, companion and system log together. Pair errors stop recording and preserve existing files. The 127,998-scalar-sample hexaphonic ring retains about 1.33 seconds at 16 kHz; the mono ring retains eight seconds. `audio timing` reports combined codec time and paired writes, with a 64,000-microsecond CRCL block budget in hexaphonic mode.

The default `cheap-crcl` feature selects CRCL v2 with no CRCL CRC or reference PCM SHA-256. MIC1 remains lossless FLAC and the paired lifecycle remains aligned; standard FLAC frame CRCs remain. To select the earlier v1 spatial codec explicitly, build with `--no-default-features --features firmware,core-smps,hexaphonic`; its quantizer has no minimum-shift policy. See the [variant definition](../../crates/services/crclencoder/cheap.md) and [historical bench results](../../servicetests/crclencoder/cheap-profiling.md).

## File-transition SD diagnostics

The default `sd-diagnostics` feature adds an observer below exFAT at the actual SDMMC read/write boundary. It captures each audio `open_ref`, `open_crcl`, `rewrite`, `close_ref` and `close_crcl` call, including failed calls. Observation starts **after acquiring the storage mutex**, so unrelated system-log writes cannot contaminate its counters. Mutex wait time is reported separately. Mono opens are covered too when that configuration enables the feature.

Each operation produces a `storage sd` header with a unique `id`, start/end system ticks, lock wait, total backend execution, success, and explicit directory-preparation call count/time. Related `storage sd_io` records share the `id` and split reads/writes into `phase=directory` and `phase=file`:

- `calls`, `sectors`, `single`, `err`: SD calls, 512-byte sectors, single-sector calls, and failed calls.
- `us`, `max_us`, `lba`, `blocks`: cumulative command wall time and the longest command's duration, volume-absolute card LBA and sector count.
- `poll_us`, `max_poll_us`: cumulative time inside SD future polls and the longest poll. These include interrupts during a poll; time outside polls includes both device waits and executor scheduling, so they do not alone prove a hardware stall.
- `seq`: longest run of adjacent single-sector writes within that phase, allowing intervening reads. Historical builds showed a 256-write run during cluster initialization; the batched implementation should no longer show that run for zeroing.

`phase=directory` covers the explicit create/ensure-parent-directory call. `phase=file` covers everything else in that operation, including directory entry scans and **directory expansion triggered inside file creation**; it does not mean exclusively audio payload. To obtain total I/O for an operation, add the disjoint directory and file counters. `dir_us` is inclusive and must not be added to backend execution time.

Directory creation and growth now zero newly allocated clusters with **16-sector writes** and no reads of the bytes being replaced. A 128 KiB cluster needs sixteen 8 KiB zero writes, plus normal filesystem metadata operations, instead of 256 read/modify/write cache operations. The temporary aligned workspace is bounded to 8 KiB at 512-byte sectors, with no heap allocation or extra PCM buffer. Overlapping cached sectors are invalidated before direct I/O, including failed/cancelled writes, so stale dirty data cannot be flushed over the zeros. Zeroing completes before new directory entries are published. Filesystem/card failures still propagate; batching is not a guarantee against long card latency.

Records use a fixed 16-operation queue, no heap or extra PCM buffers. They are emitted at no more than one operation per second, after at least two seconds without a completed critical operation and while no observation scope is active. This keeps formatting out of the close/reopen interval. Queue overflow/overlapping observation is reported as `storage sd diagnostics_lost=...`; standard logger drop/truncation counters still apply. There is no log message per sector.

Use the operation timestamps to reconstruct a particular transition, rather than adding maxima from separate diagnostic windows. Summed SD command times show how much time is inside those calls; the remainder of backend execution includes filesystem work and scheduling outside the commands. As with any instrumentation, timestamp/counter bookkeeping adds some overhead. Ordinary append/log traffic retains the existing ten-second timing summaries without detailed sector records.

Build and flash the default radio-enabled diagnostic configuration:

```powershell
rtk proxy powershell -NoProfile -ExecutionPolicy Bypass -File scripts/firmware.ps1 aardwolf
```

For mono with deep diagnostics, select `--no-default-features --features firmware,core-smps,sd-diagnostics`. Omitting `sd-diagnostics` compiles out the observer. The standalone benchmark can verify the hardware observer against its independent block-device counters with `scripts/sd_lifecycle_stress.ps1 -DeepDiagnostics`; it includes directory initialization when the chosen timestamps cross an hourly boundary.

## Radio timing diagnostics

The default `radio-diagnostics` feature adds timing around the service's `init`, `prepare`, `tx`, `rx`, `recover`, `sleep` and `wake` operations. It uses a single-owner observation scope, matching the radio service's ownership model. No allocation, formatting or SD access occurs inside driver operations. Records use a fixed 32-entry queue and are formatted by a separate task at no more than ten records per second, while no detailed SD scope is active.

- `radio timing`: operation `id`, `job`, `reason`, actual `start_ticks`/`end_ticks`, elapsed `us`, cumulative `poll_us`, longest `max_poll_us`, poll count and result. `init` reasons distinguish `startup`, `sleep_failed`, `wake_failed` and `recover_failed`; recovery reasons distinguish driver errors, timeouts and missed deadlines. Each attempted operation is counted, including failed initialization attempts. RX timeout/window closure is an expected result, not necessarily a hardware fault.
- `radio timing_error`: the concrete driver error before mapping it to a service error, including BUSY timeout or expected/actual driver state. This exposes failures in sleep/wake paths that do not necessarily increment the existing `radio_errors` counter.
- `radio timing_io`: command, manual-CS SPI transaction and BUSY-wait summaries associated with that operation ID. Fields include calls, failures, cancellations, cumulative wall/poll time, longest poll, and the longest stage's `max_us`, `tag`, `start_ticks`, `end_ticks`. `error_tag` is the last failed or cancelled command tag, even when a different successful command was longer. Command tags are numeric LR1121 opcodes (for example SET_SLEEP is 283 / `0x011b`); 65535 denotes a separate response phase. SPI/BUSY tags are zero.
- `radio timing_state` and `radio timing_request`: actual state-transition times and enable/disable requests, including job IDs, so brief `Initializing`/`Idle` transitions are visible between normal ten-second summaries.
- `radio timing_totals`: cumulative attempted operations by type, cancellations and `lost` diagnostic records. These counters survive diagnostic-queue overflow. `observer_late_us` is the worst timer wake lateness of the 100 ms reporting task in that summary window, with corresponding due/observed ticks; this is an executor-latency symptom, not proof of which driver caused it.

Cancellation is recorded by Drop guards, so a timed-out BUSY/command future or an RX cancelled by an enable change is not silently omitted. Observation generations prevent a stale stage from contaminating a later operation. Expected RX airtime, scheduled-start waits, reset delays and command waits are included in operation wall time. Long wall time with short polls indicates waiting/scheduling; long polls suggest synchronous work or interrupt time. Poll time is not a CPU-cycle measurement.

Command, SPI and BUSY timings are **nested and overlap**; do not add their totals. SPI measurements wrap the board's blocking SPI adapter, while BUSY measurements wrap its asynchronous edge wait. Match absolute system ticks against `storage sd` operation intervals, rather than comparing deferred log emission times or adding unrelated maxima. Queue `lost`, normal logger drop/truncation/failure counters and timing overhead must be checked when interpreting a run. Omitting `radio-diagnostics` compiles out its recorder and timing wrappers.

Use `scripts/crcl_decode.py` with the matching reference to verify and reconstruct six-channel WAV. It detects v1/v2 automatically and reports the absence of integrity checks for v2. Quantization precision is an evaluation setting pending beamforming and angle-of-arrival quality measurements; the successful laboratory board test does not establish acoustic calibration or GPS timing accuracy.

The microphone driver now publishes channels in PCB MK1..MK6 order. The MIC_SD2 lane assignments for MK4/MK5 were corrected following [Analysis 002](../../docs/audio/multichannel/analysis002.md). Recordings from the earlier mapping use `[MK1, MK2, MK3, MK5, MK4, MK6]` and need channels 4/5 exchanged for physical-array analysis. No file-format change is involved; use the recording's firmware identity to distinguish the two orders. `audio_doa_report.py` defaults to the corrected order; pass `--capture-order legacy` for older captures.

Every 60 seconds, `/syslog.txt` records three-axis acceleration in milli-g, three-axis magnetic field in nanotesla, and the LIS2HH12 and LIS2MDL die temperatures in milli-Celsius under `Sensor`. The `Cpu` component records average executor CPU load over the preceding 60-second window, with active, idle and elapsed milliseconds. These diagnostics also run during energy recovery. CPU idle measurement follows Integration 002 and includes interrupt work before the executor wakes. Sensor startup failures are retried each minute, and read failures are logged without stopping the app.

The firmware uses a deliberately empty global allocator. The normal exFAT mount, file lookup, create, append and flush paths use bounded storage. Any unexpected allocation fails, which makes heap use visible during bring-up. This and the seven-day data-integrity target require hardware verification.

Before a week-long campaign, verify RF packet-complete margins, GPS holdover timing, SD throughput, audio continuity while radio RX is active, the two SOC thresholds, and the card-full and card-absent cases on physical boards. Configure the antenna and regional EIRP/duty-cycle policy for the deployment; the checked-in firmware logs the antenna as `unknown` until that detail is supplied.
