# ADR-0011: Traceability and Unique Identification Driver

## Status

Proposed

---

# Context

The firmware requires a reliable way to identify the physical device and the firmware image running on it.

This is useful for:

* manufacturing traceability
* field diagnostics
* log correlation
* support workflows
* firmware auditability
* associating data files with a physical device
* confirming which firmware image produced a given dataset

The STM32U595 provides a factory-programmed 96-bit unique device identifier.

On STM32U595, this is available at:

```c
#define UID_BASE_ADDR  0x0BFA0700UL

uint32_t uid0 = *(volatile uint32_t *)(UID_BASE_ADDR + 0x00);
uint32_t uid1 = *(volatile uint32_t *)(UID_BASE_ADDR + 0x04);
uint32_t uid2 = *(volatile uint32_t *)(UID_BASE_ADDR + 0x08);
```

The raw UID is useful as a canonical identifier, but it is not always convenient for filenames, logs, support references or user-facing serial numbers. Shorter derived IDs are also required.

The firmware should also expose an identifier for the currently running firmware image. This may be calculated at runtime by hashing the firmware in flash, and ideally should also be generated by the build system and embedded as metadata.

---

# Decision

Implement a dedicated Traceability / Identity Driver.

The driver exposes:

* raw STM32 96-bit device UID
* derived 64-bit serial ID
* derived 48-bit serial ID
* derived 32-bit serial ID
* derived 16-bit short ID
* runtime firmware hash
* build-time firmware metadata, where available

The driver is read-only.

It does not own peripherals and does not require async execution.

---

# Design Goals

The Traceability Driver shall:

* Be simple.
* Be deterministic.
* Be heapless.
* Require no dynamic allocation.
* Read the STM32 factory UID.
* Provide compact derived identifiers.
* Provide firmware image traceability.
* Be safe to use early during startup.
* Be usable by Logging, Storage and diagnostic services.

---

# Non-Goals

The driver is **not** responsible for:

* cryptographic authentication
* secure boot
* anti-cloning protection
* device provisioning
* key storage
* cloud registration
* manufacturing database management

The derived serial IDs are identifiers, not security primitives.

---

# Device UID

The driver should read the STM32U595 96-bit factory UID from the documented memory-mapped UID region.

Conceptual representation:

```rust
pub struct DeviceUid {
    pub word0: u32,
    pub word1: u32,
    pub word2: u32,
}
```

The raw 96-bit UID is the canonical device identity.

Derived IDs should always be reproducible from this value.

---

# Derived Serial IDs

The STM32 UID is 96 bits wide but may contain repeated structure and limited entropy in some fields. For user-facing and compact identifiers, the driver should derive shorter IDs using a mixing function.

The derived IDs are intended for:

* filenames
* log headers
* human support workflows
* short diagnostic output
* compact telemetry identifiers

Suggested derived forms:

```rust
pub struct DeviceSerials {
    pub serial_64: u64,
    pub serial_48: u64,
    pub serial_32: u32,
    pub serial_16: u16,
}
```

The 48-bit serial may be stored in a `u64` with the upper bits cleared.

---

# Hash / Mixing Function

The derived serial IDs should be generated using a stable, deterministic mixing function.

A suitable first implementation is based on a MurmurHash3-style avalanche finalizer.

The existing C prototype is:

```c
static uint32_t device_id_32(void)
{
    uint32_t h = HAL_GetUIDw0();

    h ^= HAL_GetUIDw1();
    h ^= HAL_GetUIDw2();

    h ^= h >> 16;
    h *= 0x85EBCA6Bu;
    h ^= h >> 13;
    h *= 0xC2B2AE35u;
    h ^= h >> 16;

    return h;
}
```

The Rust implementation should provide equivalent deterministic behaviour, using explicit wrapping arithmetic.

Example conceptual Rust implementation:

```rust
fn avalanche32(mut h: u32) -> u32 {
    h ^= h >> 16;
    h = h.wrapping_mul(0x85EB_CA6B);
    h ^= h >> 13;
    h = h.wrapping_mul(0xC2B2_AE35);
    h ^= h >> 16;
    h
}
```

For 64-bit identifiers, use an equivalent 64-bit avalanche or a documented stable hash construction over all three UID words.

The chosen algorithm must be fixed and documented so serial IDs remain stable across firmware releases.

---

# Collision Expectations

Short derived IDs are not globally unique.

The raw 96-bit UID remains the authoritative identifier.

Collision risk increases as ID width decreases:

* 64-bit: suitable for compact internal identifiers
* 48-bit: suitable for filenames and user-visible serials in moderate fleets
* 32-bit: suitable for short logs and support references
* 16-bit: suitable only for local display, quick visual checks or debugging

The driver should make this distinction clear in its API documentation.

---

# Firmware Identity

The driver should expose information identifying the running firmware image.

Suggested fields:

```rust
pub struct FirmwareIdentity {
    pub runtime_crc32: Option<u32>,
    pub build_crc32: Option<u32>,
    pub git_hash: Option<&'static str>,
    pub build_timestamp: Option<&'static str>,
    pub version: Option<&'static str>,
}
```

The exact fields may evolve.

---

# Runtime Firmware Hash

The driver should be able to calculate a hash over the firmware image stored in flash.

Initial implementation may use CRC32.

Purpose:

* verify what firmware is actually present
* include firmware identity in logs
* correlate field behaviour with firmware version
* detect unexpected image changes

The runtime hash should operate over a defined flash range.

The firmware image range must be explicitly provided by linker symbols or build metadata rather than hard-coded magic values where possible.

---

# Build-Time Firmware Metadata

Ideally, the build system should also calculate the expected firmware hash and embed it into flash as metadata.

This allows comparison between:

```text
runtime-calculated firmware hash

and

build-time expected firmware hash
```

This metadata may later include:

* semantic firmware version
* git commit hash
* build timestamp
* build profile
* target board revision
* expected firmware CRC

The metadata layout should be stable and documented.

---

# Public API

Conceptual API:

```rust
pub fn read_device_uid() -> DeviceUid;

pub fn device_serials() -> DeviceSerials;

pub fn firmware_identity() -> FirmwareIdentity;

pub fn calculate_firmware_crc32() -> Result<u32, IdentityError>;
```

The final API may wrap these in an `IdentityDriver` type:

```rust
let identity = identity::init();

let uid = identity.uid();
let serial = identity.serial_32();
let fw = identity.firmware_identity();
```

The API should be synchronous and infallible where possible.

Runtime firmware hashing may be fallible if the image range is unavailable or invalid.

---

# Relationship to Logging Service

The Logging Service may use this driver to prepend device and firmware information at the start of the logfile.

Example log header:

```text
Device UID: 00112233-44556677-8899AABB
Serial32:  9F34A102
Firmware:  1.2.0
Git:       a1b2c3d
CRC32:     7C91D42E
```

The Traceability Driver should not depend on the Logging Service.

---

# Relationship to Storage Service

The Storage Service may use derived serial IDs in filenames, directory names or metadata files.

The Traceability Driver should not depend on the Storage Service.

---

# Relationship to Manufacturing

Manufacturing or provisioning tools may record:

* raw 96-bit UID
* 64-bit serial ID
* board revision
* firmware version
* calibration data

The driver only exposes identifiers. It does not implement manufacturing database logic.

---

# Error Handling

Reading the STM32 UID is expected to be infallible.

Firmware hash calculation may return errors for:

* invalid firmware range
* missing linker symbols
* unsupported flash layout
* metadata mismatch

The driver should avoid panics during normal operation.

---

# Testing

Provide a small smoke test in:

```text
drivertests/identitytest
```

The test should:

* read the raw STM32 UID
* print all three UID words
* compute 64-bit, 48-bit, 32-bit and 16-bit derived serials
* calculate the runtime firmware CRC, if available
* print build-time firmware metadata, if available

The test should verify that:

* UID reads are stable across repeated calls
* derived serial IDs are stable across repeated calls
* shorter IDs are derived deterministically from the same canonical UID
* firmware hash calculation completes successfully over the configured image range

---

# Future Extensions

Possible future additions include:

* structured device identity block in flash
* manufacturing calibration metadata
* board revision detection
* secure firmware measurement
* signature verification
* monotonic firmware version counters
* identity export over USB or RF
* QR-code-compatible serial formatting

These features should not complicate the initial read-only identity driver.

---

# Consequences

## Advantages

* Provides a single authoritative source of device identity.
* Makes logs and stored data traceable to physical hardware.
* Provides compact user-facing serial identifiers.
* Enables firmware traceability in field diagnostics.
* Keeps UID and firmware hashing logic out of higher-level services.
* Requires no heap allocation or async runtime.

## Disadvantages

* Short derived IDs are not guaranteed unique.
* Runtime firmware hashing requires a clearly defined flash image range.
* Build-time metadata requires build system support.
* Firmware hashing adds some startup or diagnostic-time cost if run frequently.

These trade-offs are acceptable because traceability is a system-wide concern and should be centralised in a small, deterministic driver.
